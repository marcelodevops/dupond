# Operator Approval Credential (`DUPOND_APPROVAL_TOKEN`)

Dupond separates **API/app authentication** from **review and delivery approval** so that callers authorized to queue or run tasks cannot automatically approve and deliver pull requests.

---

## 1. Authentication vs. Approval Credentials

| Credential | Environment Variable(s) | Purpose | How Provisioned |
| :--- | :--- | :--- | :--- |
| **App / API Auth Token** | `DUPOND_API_KEY` or `DUPOND_AUTH_TOKEN` | Authenticates general app and `/api/*` access (`Authorization: Bearer <token>` or `X-Dupond-Token: <token>`). | Operator-configured, or auto-generated by Dupond at `data/.dupond_auth_token` (`0600`) when unset. |
| **Operator Approval Token** | `DUPOND_APPROVAL_TOKEN` | Authorizes protected review approval (`POST /api/tasks/:id/review` with `decision: "approve"`) and approved delivery (`POST /api/delivery/dispatch` with `isApproved: true`) via `X-Dupond-Approval-Token`. | **Operator-configured only.** Dupond never generates, persists, or exposes `DUPOND_APPROVAL_TOKEN` automatically. |

> [!IMPORTANT]
> **Security & Storage Rules**
> - Never commit `DUPOND_APPROVAL_TOKEN` to Git or place it in shared configs.
> - Never expose an approval token in API responses, server logs, screenshots, or browser storage (`localStorage` / `sessionStorage`).
> - Dupond holds the value typed into the task panel strictly in component memory for the current request.

---

## 2. Where the Approval-Token Field Appears in the UI

In **Task Details** (`TaskDetailModal`), the Review & Delivery controls appear **only** when:
1. The task status is `review`.
2. The latest run has current, non-revoked passing authoritative verification (`verification.passed && !verification.revokedAt`) with valid candidate-binding fingerprints.

Inside that section:
- Click **`Provide approval token (if configured)`** to reveal the masked **`review-approval-token-input`** field (`type="password"`), or click **Approve Review** / **Approve & Deliver PR**—if the server requires an approval token (`403 APPROVAL_CREDENTIAL_REQUIRED`), the field opens automatically.
- Paste your `DUPOND_APPROVAL_TOKEN` into the field and submit **Approve Review** or **Approve & Deliver PR**.

## 3. Secure Generation and Configuration

Generate a strong random token (32+ bytes) and write it directly to a private `0600` environment file outside Git without printing it to your terminal. Refuse if an entry already exists so repeated runs never create duplicate lines:

```zsh
# Example using a private env file outside the repository (placeholder path)
umask 077
ENV_FILE="/path/to/private/dupond-server.env"
touch "$ENV_FILE"
chmod 600 "$ENV_FILE"
if grep -q '^DUPOND_APPROVAL_TOKEN=' "$ENV_FILE"; then
  echo "Refusing: DUPOND_APPROVAL_TOKEN already exists in $ENV_FILE" >&2
else
  printf 'DUPOND_APPROVAL_TOKEN=%s\n' "$(openssl rand -hex 32)" >> "$ENV_FILE"
fi
```

Or inject `DUPOND_APPROVAL_TOKEN` from your secret manager into the server process environment (or `.env`, which is gitignored).

## 4. Retrieving `DUPOND_APPROVAL_TOKEN` Without Exposing It

Retrieve the token from your private environment file or secret manager directly to your clipboard so it is not printed to terminal history, failing closed unless **exactly one non-empty** entry exists:

```zsh
# macOS: require exactly one non-empty DUPOND_APPROVAL_TOKEN entry and copy to clipboard
ENV_FILE="/path/to/private/dupond-server.env"
if DUPOND_TMP_TOK=$(awk '
  /^DUPOND_APPROVAL_TOKEN=/ {
    count++
    val = substr($0, index($0, "=") + 1)
  }
  END {
    if (count != 1 || val == "") {
      print "Expected exactly one non-empty DUPOND_APPROVAL_TOKEN entry" > "/dev/stderr"
      exit 1
    }
    printf "%s", val
  }
' "$ENV_FILE"); then
  printf '%s' "$DUPOND_TMP_TOK" | pbcopy
  unset DUPOND_TMP_TOK
fi

# Optional: clear clipboard after pasting into the Task Details panel
pbcopy < /dev/null
```

If using a secret manager (e.g., 1Password CLI, Vault, AWS Secrets Manager), pipe the secret read command directly to `pbcopy` (macOS) or `xclip -selection clipboard` (Linux).

## 5. Restart Requirements (Port `3000` vs. Port `3001`)

Dupond reads `process.env.DUPOND_APPROVAL_TOKEN` on the server (and `dotenv.config()` loads `.env` only at startup). After adding or rotating `DUPOND_APPROVAL_TOKEN`, **restart only the target instance** while preserving its database, state file, connection key, and profiles:

- **Main instance (port `3000`)**:
  - Uses its main environment/config and main storage (e.g., `./data/dupond.db`).
  - Restart only the port `3000` process after updating its private `.env` or secret environment.
- **Isolated test instance (port `3001`)**:
  - Uses separate disposable storage, state, connection key, and dedicated profile paths.
  - Source only its private env file (e.g., `/tmp/dupond-agy-proto-3001/server.env`) and restart only port `3001`, leaving port `3000` untouched:

```zsh
set -a && . /path/to/private/dupond-3001.env && set +a
PORT=3001 DUPOND_BIND_HOST=127.0.0.1 \
  DUPOND_DB_PATH=/path/to/disposable/dupond.db \
  DUPOND_STATE_FILE=/path/to/disposable/state.json \
  DUPOND_CONN_KEY_PATH=/path/to/disposable/conn.key \
  DUPOND_API_KEY="<your_operator_api_token>" \
  npm start
```

## 6. Troubleshooting

| HTTP / Error Code | Cause | Resolution |
| :--- | :--- | :--- |
| `503 APPROVAL_CREDENTIAL_UNCONFIGURED` | `DUPOND_APPROVAL_TOKEN` is unset or blank in the running server's environment. | Set `DUPOND_APPROVAL_TOKEN` in that instance's private `0600` env file or secret manager and restart that instance. |
| `403 APPROVAL_CREDENTIAL_REQUIRED` *(missing)* | No approval token was entered in the task panel (or no `X-Dupond-Approval-Token` header was sent). | Open **Provide approval token (if configured)** in Task Details, paste `DUPOND_APPROVAL_TOKEN`, and retry. |
| `403 APPROVAL_CREDENTIAL_REQUIRED` *(incorrect)* | The submitted token does not match the running server's `DUPOND_APPROVAL_TOKEN`, or came from a different instance (e.g. port `3000` vs. `3001`). | Re-retrieve `DUPOND_APPROVAL_TOKEN` from the target instance's private env/secret store and paste again. |

---

## 7. Evidence Requirement Still Applies

`DUPOND_APPROVAL_TOKEN` **never** bypasses verification or candidate binding. Even with a valid approval token, approval and delivery are blocked unless the run has current, non-revoked passing verification (`verification.passed && !revokedAt`) matching the exact candidate revision and requirements/configuration fingerprints.
